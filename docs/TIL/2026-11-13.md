# 1. 배운 점

- **스크린샷 테스트**: UI를 이미지로 캡처해 이전 결과와 비교, 의도치 않은 UI 변경을 검출하는 테스트.
- **`contentDescription`**: 스크린 리더(TalkBack)가 읽어줄 설명 텍스트. 시각장애인 사용자는 요소를 탭하면 설명을 듣고, **두 번 탭**하면 터치(클릭) 동작이 실행됨.
- **`OutlinedTextField`**: 테두리(아웃라인)가 있는 입력창이 필요하면 `TextField`를 꾸미는 것보다 이게 편함.

## 상태(State) 관리

> 컴포저블은 리컴포지션 때마다 함수가 다시 실행되므로, 일반 지역변수는 매번 초기화됨. 값을 유지하고 변경을 감지하려면 **Compose 전용 상태 API**를 써야 함.

- **`mutableStateOf`**: Compose가 값의 변경을 **감지**할 수 있는 상태 객체 생성. 값이 바뀌면 이를 읽는 컴포저블이 리컴포지션됨. (Int 전용은 `mutableIntStateOf`)
- **`remember`**: 리컴포지션이 일어나도 값을 **기억**. 단, **구성 변경**(화면 회전, 언어 변경 등)이 일어나면 리셋됨.
- **`rememberSaveable`**: 구성 변경이 일어나도 값이 **유지**됨.
- **사용 기준**: 화면(Screen) 단에서 유지해야 하는 상태는 `rememberSaveable`, 하위 컴포넌트 단에서는 `remember` 사용.

- by 위임 프로퍼티(Delegated Property)
  - `by`는 코틀린이 제공하는 문법적 편의(Syntactic Sugar)로, Jetpack Compose에서는 상태 값(`State`)을 `.value` 없이 일반 변수처럼 직관적으로 다룰 수 있게 해주는 기능

## Stable vs Unstable

> Compose는 파라미터가 **Stable**하고 값이 바뀌지 않았으면 리컴포지션을 **건너뜀(Skip)**. Unstable 파라미터는 변경 여부를 확신할 수 없어 다시 그림.

| **구분**    | **Stable**                                                    | **Unstable**                           |
| --------- | ------------------------------------------------------------- | -------------------------------------- |
| **예시**    | 프리미티브 타입(Int, Boolean 등), `String`, `val`만 가진 불변 `data class` | `var` 프로퍼티를 가진 클래스, `List` 등 컬렉션 인터페이스 |
| **리컴포지션** | 값이 같으면 건너뜀(.equals())                                         | 무조건 다시 그림 (기존 방식)                      |


- **파라미터는 가변(Mutable) 대신 불변(Immutable)으로 전달**하는 것이 원칙.
- **예전 방식**: `List` 대신 `ImmutableList`(kotlinx.collections.immutable)를 전달해 불필요한 리컴포지션을 줄였음.
- **최신 버전**(Kotlin 2.0.20): Strong Skipping 모드가 기본 활성화되어 `List<>` 같은 Unstable 파라미터도 **같은 인스턴스(동일성)면 리컴포지션을 건너뜀** -> 사실상 Stable처럼 동작.
- 기존 비교 방식
  - **불안정한(Unstable) 매개변수가 하나라도 있는 경우:** 비교를 시도조차 하지 않고 무조건 재구성(Recomposition)됨. (아예 스킵 대상에서 제외됨)
- Strong Skipping 비교 방식
  - 불안정한 매개변수(Unstable)는 동일성 (`===`)을 사용하여 비교
  - 안정적인 매개변수(Stable)는 동등성 (`Object.equals()`)을 사용하여 비교

## 상태 호이스팅 (State Hoisting)

> 상태를 컴포저블 **내부가 아닌 바깥(상위)에 두고**, 하위 컴포저블은 **받은 값대로 그리기만** 하는 패턴. Compose에서 가장 기본이 되는 패턴.

- 상태가 필요한 컴포저블은 **내부에서 관리하지 않고, 외부에서 관리**하도록 상태를 끌어올림.
- **예외**: `Button`은 눌림 효과(ripple) 같은 UI 표현용 자체 상태를 내부에 가짐.
- 하위 컴포저블은 **값(state)** 과 **이벤트 콜백(onXxx)** 만 파라미터로 받음.
- **재사용성:** UI 컴포넌트를 독립시켜 여러 곳에서 재사용 가능
- **테스트 용이성:** 상태 관리 로직이 분리되어 유닛 테스트가 쉬움
- **관심사 분리:** UI(그리기)와 로직(상태 관리)이 명확히 분리됨
- **단일 진입점(SSOT):** 데이터 흐름이 단순해져 상태 동기화 오류 및 버그 예방

## AI로 코딩할 때 머리에 남기는 7가지 방법

1. **먼저 해보기**: 시키기 전에 내 방식대로 생각하거나 대충 짜본 뒤 AI 답과 비교 (차이 난 부분이 제일 오래 남음)
2. **힌트만 요청**: "코드 말고 방향만", "어디가 틀렸는지 힌트만"
3. **설명 못 하면 안 쓰기**: 한 줄씩 왜 필요한지 답해보고, 복붙 말고 직접 타이핑
4. **거꾸로 검사받기**: 내가 설명하고 AI가 지적하게 하기, 퀴즈 내달라고 하기
5. **다시 짜보기**: 며칠 뒤 AI 없이 같은 기능 재구현 (막히는 곳이 모르는 부분)
6. **3줄 기록**: 뭘 배웠나 / 뭐에 막혔나 / 다음엔 어떻게 할까
7. **모드 나누기**: 배우는 영역은 선생님처럼 쓰고, 아는 반복 작업은 맡기기
